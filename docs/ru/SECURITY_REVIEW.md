# Pinguva Agent - описание для службы информационной безопасности клиента

Документ описывает агент на стороне клиента по открытому исходному коду версии `0.2.23`. Это описание потоков данных, а не сертификат безопасности и не описание закрытого backend Pinguva. [English version](../en/SECURITY_REVIEW.md) имеет ту же область применения.

## Что устанавливается

Pinguva Agent работает на Linux- или Windows-сервере клиента. Примерно раз в минуту он собирает технические показатели сервера и отправляет отчёт на настроенный сервер Pinguva. Дополнительные интеграции на Linux могут читать выбранные локальные журналы и системные представления СУБД. Проверки Bitrix24 REST используют webhook, сохранённый на сервере клиента. Агент не открывает входящий порт и не принимает удалённые команды от Pinguva.

Установку или обновление бинарного файла запускает администратор командой из карточки сервера. Доступ к локальным файлам, права интеграций и правила межсетевого экрана согласует клиент. Само подключение агента не предоставляет Pinguva интерактивный SSH-доступ к серверу.

## Сетевые потоки и протоколы

| Поток | Направление | Протокол | Когда | Что передаётся |
| --- | --- | --- | --- | --- |
| Регистрация | Агент -> настроенный `AGENT_SERVER` | HTTP POST `/api/agent/enroll`, в production - HTTPS | Первая установка или повторная регистрация | Начальный отчёт с телеметрией; временный токен в заголовке `Authorization: Bearer`. В ответе - ID агента и постоянный токен. |
| Обычный отчёт | Агент -> настроенный `AGENT_SERVER` | HTTP POST `/api/agent/report`, в production - HTTPS | Примерно раз в 60 секунд | JSON с телеметрией и включёнными сводками; постоянный токен в Bearer-заголовке. Ответ может содержать выбранные маршруты, подсказки путей журналов и флаг диагностики Bitrix24. Поля для shell-команд в ответе нет. |
| Дополнительная история | Агент -> тот же сервер | HTTP POST `/api/agent/v1/bitrix24-diagnostics` или `/api/agent/v1/database-diagnostics`, в production - HTTPS | Только при включённой локальной интеграции Linux | Ограниченные события диагностики и подтверждения приёма. |
| Проверка Bitrix24 REST | Агент -> настроенный клиентом портал Bitrix24 | HTTPS | Только после локальной настройки webhook | Выбранные REST-проверки с локальным webhook. Pinguva получает сводку, а не webhook или тело ответа CRM. |
| Чтение журналов и СУБД | Агент -> локальная файловая система или клиент СУБД | Чтение файла, клиент/сокет СУБД согласно настройке | Только для включённых интеграций | Исходные данные обрабатываются локально и сворачиваются в технические показатели. Конфигурация клиента СУБД может влиять на способ подключения. |
| Установка/обновление | Команда администратора -> сервер распространения Pinguva | Загрузка по HTTPS | Только при запуске команды администратором | Установочный скрипт и бинарный файл агента; это не периодический отчёт. |

Для штатного развёртывания достаточно разрешить исходящий TCP 443 к `monit.pinguva.com`. Доступ к порталу Bitrix24 нужен только при включённых REST-проверках. Для показателя Ping агент также открывает короткое исходящее TCP-соединение к настроенному хосту Pinguva. Входящее правило для самого агента не требуется. Перед согласованием проверьте значение `AGENT_SERVER`: код допускает произвольный HTTP-адрес для разработки и **не принуждает** к HTTPS. В production необходимо указать `https://` и проверять сертификат обычным механизмом TLS. В коде агента не настроен обход проверки TLS-сертификата.

## Что агент передаёт в Pinguva

| Режим | Какие поля или категории могут покинуть сервер клиента |
| --- | --- |
| Базовый отчёт | ID агента и установки, отображаемое имя, hostname, IP сервера, ОС/платформа/версия ядра/архитектура, версия агента, время отчёта, CPU/load/ядра, память, диски, скорость сети и дискового ввода-вывода, uptime, Ping, ограниченное поле ошибки/статуса. |
| Настроенное наблюдение Linux | Названия и статусы служб. Для выбранных конфигурационных профилей - ключ профиля, путь файла, тип, факт существования, время изменения, размер и SHA-256; **не** содержимое файла. |
| Настроенный Bitrix24 | Статус проверки, выбранный REST-метод/профиль, время ответа, безопасное количество результатов и очищенная категория ошибки; агрегаты маршрутов access-log и 5xx; счётчики MySQL, digest и ожиданий блокировок. Запись digest иногда содержит обезличенную структуру `SELECT` и имя схемы, если нормализация успешна. |
| Настроенная диагностика СУБД | Тип и версия СУБД, метаданные экземпляра или адреса подключения, счётчики соединений и активности, ожидания и блокировки, технические группы запросов, digest/hash, операция и имя БД при наличии. |
| Настроенный мониторинг бизнес-API | Заданное название, HTTP-метод и нормализованный путь маршрута; минутные счётчики запросов, групп ответов и кодов ошибок; средняя/максимальная задержка при наличии времени в журнале; сводка источников трафика. Обнаружение источника журнала дополнительно может передавать **полный локальный путь к файлу**, статус и найденные безопасные названия/методы/пути маршрутов. |

Hostname, IP сервера, пути файлов, имена баз/схем, названия маршрутов и адреса источников - технические метаданные, но они тоже могут быть чувствительными. Текущая функция сводки сокращает типичные строки, похожие на IP; другие значения `source` могут пройти в отчёт (до 80 символов). Не включайте пароли, ID клиентов или персональные данные в названия маршрутов, пути файлов и поле `source` журнала. Согласуйте область наблюдения до включения интеграции.

## Что остаётся на стороне клиента

Код отправки отчёта не передаёт URL webhook Bitrix24, пароли СУБД, OAuth/API-токены, записи CRM, исходные значения SQL, сырые строки access-log, содержимое конфигурационных файлов, тела HTTP-запросов и ответов, cookies и заголовки авторизации исходных API-запросов. Агент разбирает локальные журналы и считает агрегаты по совпавшим маршрутам. Параметры URL после `?` исключаются, динамические части пути нормализуются. В окне ошибок показываются количество и HTTP-код за интервал, а не отдельные запросы с точным временем каждого ответа.

Есть отдельное исключение: **токен самого агента передаётся** серверу Pinguva в HTTPS-заголовке `Authorization: Bearer` для аутентификации отчёта. Он не является полем JSON-телеметрии. Считайте его секретом; не публикуйте заголовки, state-файлы и дампы трафика. На Linux агент записывает state-файл с правами `0600`; стандартный путь - `/var/lib/pinguva-agent/state.json`. На Windows стандартный путь - `%ProgramData%\Pinguva\agent\state.json`: его ACL необходимо проверить и ограничить отдельно, поскольку Unix-права не задают политику ACL Windows. Webhook Bitrix24 после явной настройки хранится в `/etc/pinguva-agent/bitrix24.json`. Файл `/root/.my.cnf` применяется только если проходит строгую проверку владельца и прав `0600`; иначе используется предусмотренный локальный способ подключения.

Перечень исключений описывает реализованные сборщики, но не означает, что произвольные названия маршрутов и пути, заданные клиентом, автоматически безопасны. Сырые журналы должны оставаться закрытыми; агенту следует давать доступ только к выбранным источникам.

## Пример обмена

Ниже полностью вымышленные и сокращённые фрагменты, показывающие форму протокола. Это не полный рабочий пакет и не данные клиента. Никогда не прикладывайте действующий Bearer-токен к заявке на согласование.

```http
POST /api/agent/report HTTP/1.1
Host: monit.pinguva.com
Content-Type: application/json
Authorization: Bearer <REDACTED_AGENT_TOKEN>

{"agentId":"agt_example","hostname":"example-host","ip":"192.0.2.10","os":"linux","version":"0.2.23","cpuPercent":12.5,"memoryPercent":38.0,"reportedAt":"2026-01-01T00:00:00Z"}
```

При включённом мониторинге бизнес-API в отчёте может быть такой агрегат:

```json
{
  "businessApiDiagnostics": [{
    "bucketStart": "2026-01-01T00:00:00Z",
    "bucketSeconds": 60,
    "routes": [{
      "name": "Example operation",
      "method": "POST",
      "path": "/api/orders/:value",
      "requests": 12,
      "serverErrors": 2,
      "errorStatusCodes": [{"code": 503, "count": 2}],
      "latencyAvailable": true,
      "averageLatencyMs": 146,
      "maxLatencyMs": 1250
    }]
  }]
}
```

Ответ на обычный отчёт может включать настройки, например `businessApiEndpointWatches` с шаблонами маршрутов и `bitrix24LoadDiagnosticsEnabled`. Это ответ на исходящий запрос агента, а не удалённая shell-сессия.

## Контрольный список для ИБ

1. Согласуйте версию агента и изучите код каталога [`0.2.23`](../../0.2.23/), особенно `main.go`, `business_api_diagnostics.go`, `bitrix24_load_diagnostics.go` и `database_diagnostics.go`.
2. Проверьте HTTPS в `AGENT_SERVER`, разрешённый адрес назначения и отсутствие входящего порта агента.
3. Отдельно согласуйте права webhook Bitrix24, привилегии СУБД, пути журналов и профили наблюдаемых файлов. Неиспользуемые интеграции не включайте.
4. Без просмотра содержимого секретных файлов проверьте локального пользователя службы, входящие сокеты и права state-файла:

   ```bash
   sudo systemctl show pinguva-agent -p User -p Group
   sudo ss -ltnp | grep pinguva-agent || echo 'No agent listening socket'
   sudo stat -c '%a %U:%G %n' /var/lib/pinguva-agent/state.json
   ```

5. Перед передачей журналов или снимков экрана третьей стороне удалите токены, заголовки, имена серверов, IP, пути и данные клиентов. Не публикуйте сетевые дампы и внутренние документы клиента.

На Windows стандартное имя службы - `PinguvaAgent` (его можно изменить при установке). Эти команды показывают учётную запись службы и ACL state-файла, не читая сам токен:

```powershell
Get-CimInstance Win32_Service -Filter "Name='PinguvaAgent'" | Select-Object State, StartName, ProcessId
Get-Acl "$env:ProgramData\Pinguva\agent\state.json" | Format-List Path, AccessToString
```

Открытый репозиторий не подтверждает сроки хранения, регион размещения, права доступа, резервное копирование и порядок реагирования на инциденты в закрытом SaaS. Эти условия необходимо отдельно запросить у Pinguva через [официальный сайт](https://pinguva.com). Сообщение об уязвимости направляйте по процедуре [SECURITY.md](../../SECURITY.md).
