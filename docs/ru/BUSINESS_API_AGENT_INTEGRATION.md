# Мониторинг бизнес-API через Pinguva Agent

Этот сценарий нужен, когда у клиента есть собственные API-маршруты и нужно быстро
видеть нагрузку, ошибки и задержки без доработки backend-кода клиента.

## Что требуется

- Linux-сервер с установленным Pinguva Agent `0.2.19` или новее.
- Стандартный access-log Nginx или Apache на одном из путей:
  - `/var/log/nginx/access.log`;
  - `/var/log/nginx/api.access.log`;
  - `/var/log/apache2/access.log`;
  - `/var/log/httpd/access_log`.
- Тариф Pinguva `Enterprise`.

## Как настроить

1. Откройте `Интеграции и API`.
2. Откройте `Мониторинг бизнес-API`.
3. Раскройте `Настройки подключения`.
4. Выберите Linux-сервер.
5. Нажмите `Добавить маршрут` и заполните форму.
6. В поле `URL или путь маршрута` укажите полный URL или только путь. Например,
   `https://api.example.kz/api/orders/:id` будет сохранён как
   `/api/orders/:value`. Домен и query-параметры не сохраняются и не
   передаются.
7. Выберите HTTP-метод, при необходимости укажите путь к журналу, настройте
   правила уведомлений и нажмите `Добавить маршрут`.

Выберите `ANY`, если маршрут должен учитывать любой HTTP-метод.

Путь к журналу необязателен. Агент `0.2.19` сначала проверяет стандартные пути и
читает активные директивы `access_log` в Nginx и `CustomLog` или `TransferLog` в
Apache. Указывайте путь вручную только если журнал не описан в конфигурации
веб-сервера. Файл остаётся на сервере клиента.

Агент также поддерживает журналы, где длительность находится внутри даты, а код
ответа расположен перед HTTP-запросом:

```text
203.0.113.10 - - [08/Oct/2026:21:40:58 +0500 - 0.146] 200 "POST /api/customer.segment HTTP/1.1" 272 "-" "GuzzleHttp/7" "-"
```

Версия `0.2.19` дополнительно сопоставляет именованные параметры пути, например
`/api/orders/:order_id`, с любым одним фактическим сегментом пути. Поэтому
значения вроде UUID, числового идентификатора и произвольного кода клиента не
требуют отдельного маршрута. Агент также распознаёт распространённые варианты
Nginx и Apache с запросом в кавычках или без кавычек, ISO-время и JSON access-log
с полями `request` или `request_method`/`request_uri`, `status` и временем
обработки. Нестандартный журнал должен быть явно указан в настройке маршрута.

### Журналы приложения и автоопределение формата

Агент локально определяет распространённый формат журнала. Поддерживаются
стандартные строки Nginx/Apache, JSONL и многострочный PHP/cURL-дамп с полями:

```text
Код ответа - 200
[url] => https://api.example.kz/api/orders
[http_code] => 200
[total_time] => 0.843471
```

Для многострочного журнала укажите абсолютный `Log path` конкретного маршрута.
Если в блоке нет HTTP-метода, он сопоставляется с настроенным методом маршрута
и только с указанным файлом. Если файл читается, но ни один поддерживаемый блок
не найден, Pinguva показывает, что формат не распознан, а не нулевой трафик.

Начиная с агента `0.2.20`, состояние каждого указанного файла отображается
отдельно: файл не найден, нет прав на чтение или формат не распознан. Доступный
стандартный access-log не скрывает ошибку пути журнала приложения. Путь должен
существовать на выбранном сервере с агентом, а не на сервере платформы.
Проверьте точный путь и доступ без просмотра содержимого файла:

```bash
sudo -u pinguva-agent test -r /absolute/path/to/app/log/request_orders.txt \
  && echo readable || echo missing_or_denied
sudo stat -c 'modified=%y size=%s' /absolute/path/to/app/log/request_orders.txt
```

После исправления пути агент считает последнюю завершённую минуту. Записи,
созданные до настройки маршрута, не загружаются задним числом. Для проверки
нужен новый запрос по маршруту и 1-2 минуты до очередного отчёта агента.
Email-события отправляются только если в настройке маршрута включена почта,
сработало правило уведомления и email-канал рабочего пространства включён.

Агент отправляет только агрегаты. Тела ответов, заголовки, токены, UUID,
параметры URL и исходные строки журнала остаются на сервере клиента.

### Если access log недоступен

Агент читает журнал от имени системного пользователя `pinguva-agent`, а не от
имени `root`. Проверьте пользователя службы и чтение файла:

```bash
sudo systemctl show pinguva-agent -p User -p Group
sudo -u pinguva-agent head -c 1 /var/log/nginx/access.log >/dev/null \
  && echo readable || echo denied
```

Если файл принадлежит `bitrix:adm` и имеет права `0640`, выдайте агенту только
необходимый доступ через ACL:

```bash
sudo setfacl -m u:pinguva-agent:rx /var/log/nginx
sudo setfacl -m u:pinguva-agent:r /var/log/nginx/access.log
sudo systemctl restart pinguva-agent
```

Для журнала приложения в закрытом каталоге выдайте `pinguva-agent` право прохода
по каждому родительскому каталогу и право чтения только нужного файла:

```bash
sudo setfacl -m u:pinguva-agent:--x /opt/app /opt/app/log
sudo setfacl -m u:pinguva-agent:r /opt/app/log/request_orders.txt
```

Замените пути на фактические и проверьте результат от имени службы. Не выдавайте
агенту доступ ко всему каталогу, если для маршрута указан один файл.

Для Apache укажите фактический каталог и файл журнала. Не используйте `chmod
644`: это откроет журнал всем локальным пользователям. После изменения проверьте
журнал агента:

```bash
sudo journalctl -u pinguva-agent -n 50 --no-pager \
  | grep -E 'access log|business API|report sent'
```

Сообщение `access log недоступен` означает, что агент не смог открыть подходящий
файл. Значение `запросов: 0` означает, что файл открыт, но в текущем окне нет
запросов выбранного маршрута. Если ротация создаёт новый файл, сохраните ACL в
настройках `logrotate` или добавьте `pinguva-agent` в группу чтения журналов.
Группа открывает доступ и к другим файлам этой группы, поэтому ACL для одного
файла обычно безопаснее.

Пример:

```text
GET /api/orders
POST /api/orders/:order_id/status
GET /api/loyalty/services/consumers/:uuid
POST /api/leads/actions
```

Можно вставлять полный URL. Pinguva сохранит только путь, без домена и query
string.

## Что передаётся в Pinguva

Агент отправляет только агрегированную техническую сводку:

- маршрут;
- HTTP-метод;
- количество запросов;
- успешные ответы;
- бизнес-отказы `400`, `409`, `422`;
- клиентские и серверные ошибки;
- средняя и максимальная задержка, если она есть в формате access-log;
- маскированные источники трафика.

## Что не передаётся

Агент не отправляет:

- тела запросов;
- тела ответов;
- HTTP-заголовки;
- cookies;
- query string;
- токены;
- сырые access-log;
- персональные данные.

## Важная особенность задержек

Nginx и Apache не всегда пишут время обработки запроса в стандартный access-log.
Если request time отсутствует, Pinguva покажет запросы и ошибки, но задержка
будет недоступна до настройки формата журнала.
